## Summary
CURRENT DESIGN (src). Two layers.
(a) mem (src/mem.cpp): mem::Load(name) maps .text/.rdata/.data of a loaded module (GetModuleHandleA). mem::FindAll/Find scan only the in-memory .text with an IDA-style spaced pattern ("48 8B 0D ? ? ? ?", single or multiple '?' = one wildcard byte), memchr on the first byte. mem::Rel(insn, dispOffset, length) = insn + length + int32(insn+dispOffset). mem::VTable(module, ".?AVName@@") finds an RTTI type descriptor name in .data (td = name-0x10, 8-aligned), then a CompleteObjectLocator in .rdata with signature 1, offset 0, pTypeDescriptor RVA == td, pSelf RVA == itself, then the .rdata qword pointing to the COL; vtable = that qword + 8. This is the primary vtable only. mem::StaticInstance finds the first .data qword equal to the vtable address, i.e. a static object. mem::Interface calls the module's exported CreateInterface(name, nullptr).
(b) patterns registry (src/core/patterns.cpp): patterns::Find/FindAll/FindRef wrap mem::Find* and record {name, module, pattern, RVA, status, matches} into a mutex-protected vector. patterns::Note records non-pattern addresses (vtable/global/iface/convar). Find never checks uniqueness (matches=-1). A lazily created worker thread runs Verify (counts matches in the on-disk .text read with CreateFileA, so hooks do not disturb it), Generate (hde64-based unique-signature generator, up to 40 instructions/96 bytes; it wildcards rel operands and RIP disp32, and every disp32 when looseOffsets is set), GenerateAt(module, rva) and Export (patterns.txt next to the settings file). Menu UI is at menu.cpp:1125-1200. Shutdown runs on the Unload event (wiring.cpp:136).
Data flow: dllmain waits for client.dll, then calls hooks::Init. hooks::Init retries game::Init up to 50 times, 200 ms apart, rescanning about 70 signatures on every try. Next it hooks DXGI Present and ResizeBuffers through a dummy swapchain vtable (8/13) and FrameStageNotify through Source2Client002 vtable[36]. Then movement::Install (CCSGOInput RTTI vtable[5] CreateMove, plus GetUserCmd and MergeSubtick by signature), misc::Install (CameraThink by signature) and hands::Install (scenesystem CAnimatableSceneObjectDesc RTTI vtable[1]) run. wiring then runs ray/Hitboxes/Spread/JumpCheck/damage::Init.
Most current "signatures" are not function signatures. About 75 of them read a struct offset out of an instruction displacement (game.cpp:94-167, jumpcheck.cpp:54-58, damage.cpp:42-46, spread.cpp:175-192, hitbox.cpp:86-103). ConVars are found by scanning client.dll .rdata for the name string, then .text for "48 8D 15 <rip->name>", then the first "48 8D 0D" within 0x90 bytes (game.cpp:513-544).
OWNER DESIGN (ref). game_addresses.hpp declares every address as a constexpr address_t entry in a "_addr" section, keyed by FNV-1a32 of the full string (basis 0x811C9DC5, prime 0x01000193) and typed pattern/interface_/convar/module_base/module_export. PATTERN(entry) expands to a lambda with a function-local static: memory::resolve_pattern(entry.data.data). INTERFACE_("module:Name") calls memory::get_module_interface. CONVAR("name") calls addresses::globals::cvar->find(hash(name)), returning c_convar* with get<T>(). MODULE_BASE and MODULE_EXPORT also exist; MODULE_EXPORT retries while the result is 0. patterns.cpp holds 166 pattern entries. All of them are code patterns in the form "module.dll:HEX[suffix]".
PATTERN STRING SYNTAX (derived from all 166 entries, validated by script: hex is uppercase and even-length, wildcards are always '??', at most one marker per pattern, suffix regex ^[0-9A-F?*>]+([+-][0-9A-F]+)?(~)?$):
- "module:" prefix: the module is looked up with GetModuleHandle. Modules used: client, engine2, scenesystem, rendersystemdx11, tier0, materialsystem2, filesystem_stdio, resourcesystem, soundsystem, particles, matchmaking (all .dll).
- Body: pairs of hex digits, each one byte; "??" = any byte; no spaces.
- '*' (zero width, placed before the 4 bytes of a RIP-relative disp32): result = M + 4 + int32(M), with M = match + byteIndex(marker). In every owner use the disp32 is the last field of the instruction (488D05/488D0D lea, 488B05/0D/1D/35 mov, 48391D cmp, 488905 mov store, 8B3D, 486315 movsxd, 0FB705 movzx, 4C3905 cmp). So M+4 is the next instruction and the rule is exact. It would be wrong for an instruction with a trailing immediate, such as C705 disp imm32; the resolver should document that it does not support that case. tools/sigscan.py uses the same rule (p + 4 + rel).
- '>' (zero width, always placed right before an E8 or E9 byte): result = M + 5 + int32(M + 1), i.e. follow the call or jmp.
- No marker: result = match address. Most of these are function starts. draw_smoke_array_fallback is matched mid-function and corrected by an offset.
- Suffix '+HEX' or '-HEX' (hexadecimal, added after marker resolution): proven by draw_smoke_array_fallback "…E8-20". Its body 4D8BF8488BFA488BF1 sits exactly 0x20 bytes into draw_smoke_array (5+5+5+1+2+2+4+8 = 32 prologue bytes), so the result = match - 0x20 = function start. It is also proven by create_move "+28~" = CCSGOInput vtable + 0x28 then deref = vtable[5], the same index current movement.cpp:484 uses, and by draw_scene_object "+8~" = vtable[1], the same as hands.cpp:212.
- Suffix '~': dereference once, result = *(uintptr_t*)result, applied after the offset. "+N~" therefore means vtable entry N/8 when '*' resolved to a vtable from a lea. A bare "~" on a "488B0D*" global means pointer value instead of pointer address (game_event_manager, game_trace_manager, parse_report_hit/service_read = vtable[0]). "+8" without '~' (light_data_queue) means address of global + 8.
- Without '~', a mov-style global ("488B0D*", "488B05*") returns the ADDRESS of the global, so the consumer must read it. The ref does this: read<uintptr_t>(global_vars) + 0x44 = tick count. A lea-style global (csgo_input, view_matrix, weapon_recoil_data, frame_input_ring_base) returns the object itself.
resolve_pattern(str) algorithm:
1. Split at the first ':'. base = GetModuleHandleA(module); if 0, return 0.
2. Parse the body left to right. On '*' or '>', record markerIndex = bytes emitted so far and the marker kind. On "??", emit a wildcard byte. Otherwise read two hex digits as one byte. Stop at '+', '-' or '~'. Then parse an optional sign plus hex offset, then an optional '~'.
3. Scan the module's executable section(s) (.text) for the first match. Return 0 if none. Optionally count matches in debug builds and warn when there is more than one.
4. addr = match. For '*': addr = match + mi + 4 + *(int32*)(match + mi). For '>': addr = match + mi + 5 + *(int32*)(match + mi + 1); optionally assert that the byte at match+mi is E8 or E9.
5. addr += sign * offset.
6. If '~': return 0 when addr is not readable (SEH or a module range check), else addr = *(uintptr_t*)addr.
7. Return addr.

## Recode notes
1) RESOLVER (memory::resolve_pattern). Implement the algorithm given in the summary exactly.
Grammar: module ':' body suffix, where
- body = { HEXHEX | '??' | '*' | '>' } (at most one marker)
- suffix = [ ('+'|'-') HEX+ ] [ '~' ]
- '*' -> M+4+int32(M)
- '>' -> M+5+int32(M+1)
- then add the hex offset
- then deref once if '~'
Scan only executable sections of the named module. Use SEH or a range check before '~'.
Cache per entry, not per call site. Warm up all entries on the loader thread, log count/RVA and flag ambiguous ones. Treat a 0 result as retryable for '~' entries that point at runtime globals.
Keep the useful parts of the current registry as a dev tool: the Verify match counter, the hde64 unique-sig generator emitting owner syntax, and Export. Accept only owner syntax.
Conversions:
- An IDA string becomes owner syntax by removing spaces and turning '?' into '??'.
- FindRef(p,3,7) or Rel(p+k,3,7) becomes '*' before the disp.
- Rel(p+k,1,5) becomes '>' before the E8.
The owner syntax has NO operator for 'read the int32/int8 displacement as a struct offset'. Every current offset-extraction sig must become SCHEMA or an owner-supplied constant/pattern, or the syntax needs an extension (e.g. '#4'), which must be agreed with the owner.
